## 3. Контрольные вопросы и ответы

### 1. Что такое обмен сообщениями (messaging) и какие проблемы в архитектуре ПО он решает?
Обмен сообщениями — это передача данных между компонентами через сообщения. Он уменьшает связанность сервисов, позволяет работать асинхронно, распределять нагрузку и временно сохранять задания, если получатель занят.

### 2. Что такое брокер сообщений? Какова его роль в системе?
Брокер сообщений — промежуточный сервер между отправителем и получателем. Он принимает сообщения, маршрутизирует их, помещает в очереди и передаёт потребителям по заданным правилам.

### 3. Перечислите и охарактеризуйте основные шаблоны (паттерны) обмена сообщениями.
Основные паттерны: **point-to-point** — сообщение получает один потребитель; **work queue** — задания распределяются между работниками; **publish/subscribe** — публикация поступает нескольким подписчикам; **routing** — доставка по ключу или правилу; **request/reply** — запрос и ответ; **event streaming** — запись событий в журнал с последующим чтением.

### 4. Дайте определение RabbitMQ.
RabbitMQ — брокер сообщений, который обеспечивает обмен данными между приложениями через обменники, очереди и потребителей. Он поддерживает асинхронное взаимодействие и несколько протоколов.

### 5. Какой прототокол лежит в основе RabitMQ?
Для примеров на Python с библиотекой Pika используется **AMQP 0-9-1** (Advanced Message Queuing Protocol). RabbitMQ также поддерживает другие протоколы, например AMQP 1.0.

### 6. В RabbitMQ сообщения, принятые от приложения-продюсера (издателя), записываются …
Сообщения маршрутизируются через **exchange** и попадают в **очереди (queues)**, откуда их получают потребители.

### 7. Объясните, что такое точка обмена (exchange).
Exchange — компонент RabbitMQ, который принимает публикации от продюсера и выбирает подходящие очереди по типу обменника, ключу маршрутизации и привязкам.

### 8. Что такое Binding в RabbitMQ?
Binding — правило, связывающее очередь с обменником. Оно может содержать binding key и определяет, какие сообщения направляются в эту очередь.

### 9. Дайте определение Routing Key в Rabbit MQ.
Routing key — строковый ключ, указанный продюсером при публикации. Обменник использует его для выбора маршрута; например, `direct` сравнивает ключ точно, а `topic` — по шаблону.

### 10. Опишите по шагам процесс маршрутизации сообщения в RabbitMQ (от продюсера до потребителя).
1) Продюсер публикует сообщение в exchange с routing key. 2) Exchange анализирует bindings. 3) Сообщение направляется в подходящие очереди. 4) Очередь хранит сообщение до доставки. 5) Потребитель получает и обрабатывает сообщение. 6) При ручном подтверждении потребитель посылает `ack`; после подтверждения брокер завершает доставку.

### 11. Если необходимо просто распараллелить обработку сообщений, принятых от продюсера (издателя) по нескольким потребителям, какой тип обменника надо выбрать в RabbitMQ?
Можно использовать **direct exchange** (в том числе встроенный обменник по умолчанию) и **одну общую очередь** с несколькими конкурирующими потребителями. Тогда конкретное сообщение получает только один из них. `fanout` с отдельными очередями здесь не подходит, так как дублирует сообщение.

### 12. Какие типы точек обмена (exchanges) существуют в RabbitMQ и в чем их принципиальные отличия?
Основные типы: **direct** — точное совпадение routing key; **fanout** — отправка во все привязанные очереди без учёта ключа; **topic** — сопоставление ключа по шаблону (`*`, `#`); **headers** — маршрутизация по заголовкам сообщения. Также существует встроенный default exchange типа direct.

### 13. Обычно приложение-продюсер отправляя сообщение в RabbitMQ, отправляет его ……
В **exchange**, а не непосредственно в очередь. При использовании обменника по умолчанию (`exchange=""`) сообщение выглядит как отправка в очередь по её имени, но технически проходит через default exchange.

### 14. Как предотвратить потребление устаревших данных из RabbitMQ?
Установить TTL (время жизни) для сообщения или очереди, настроить dead-letter exchange для просроченных сообщений. Если это важно для бизнес-логики, потребитель дополнительно проверяет дату или версию данных.

### 15. По какому принципу LIFO или FIFO устроены очереди в RabbitMQ, в которые записываются сообщения?
Обычно применяется **FIFO** (первым пришёл — первым вышел). Порядок наблюдаемой обработки может меняться при нескольких потребителях, повторной доставке или использовании приоритетов.

### 16. Для чего предназначен Server (Broker/Node) в RabbitMQ.
Node — экземпляр сервера RabbitMQ, который обрабатывает подключения, обменники, очереди и доставку сообщений. Несколько узлов могут образовывать кластер.

### 17. Опишите назначение Virtual Host (Vhost) в RabbitMQ.
Virtual Host — логическая область изоляции ресурсов RabbitMQ: обменников, очередей и прав доступа. Он позволяет нескольким приложениям использовать один брокер независимо друг от друга.

### 18. Что такое подтверждение сообщений (acknowledgments /ack, nack, reject) и зачем оно необходимо?
`ack` подтверждает успешную обработку сообщения. `nack` сообщает о неуспехе или невозможности обработки, может применяться к нескольким сообщениям. `reject` отклоняет одно сообщение. Для `nack` и `reject` можно указать повторную постановку в очередь или отказ от неё. Подтверждения уменьшают риск потери заданий при сбоях потребителя.

### 19. Чем отличаются долговечные (durable) и временные (transient) очереди и сообщения? Как это влияет на перезагрузку брокера?
Durable-очередь сохраняет своё определение после перезапуска брокера, а недолговечная очередь обычно не сохраняется. Persistent-сообщения предназначены для сохранения на диске, transient-сообщения не имеют такой гарантии. Для сохранения сообщений при перезапуске обычно требуются долговечная очередь и persistent-сообщения; для более надёжной публикации используют publisher confirms.

### 20. Что такое Dead Letter Exchange (DLX) и какие сценарии его использования?
DLX — обменник, куда брокер перенаправляет сообщения из исходной очереди при отклонении без повторной постановки, истечении TTL, превышении лимита длины очереди или некоторых лимитов повторной доставки. Применяется для анализа ошибок, повторных попыток и обработки «плохих» сообщений.

### 21. Что такое Priority Queue в RabbitMQ и как она работает?
Priority Queue позволяет обслуживать сообщения с учётом приоритета. Продюсер указывает значение priority, а очередь с поддержкой приоритетов старается доставлять сообщения более высокого приоритета раньше обычных. Это меняет стандартный FIFO-порядок.

### 22. Дайте определение Apache Kafka. Какие основные задачи она решает и чем ее философия отличается от классических брокеров?
Apache Kafka — распределённая платформа потоковой передачи и хранения событий. Она применяется для сбора данных, интеграции сервисов, аналитики и обработки потоков в реальном времени. В отличие от традиционной очереди, Kafka хранит события в журнале по политике retention, а потребители читают их по смещениям (offsets).

### 23. Опишите архитектуру Kafka. Что такое Broker, Topic и Partition?
Broker — сервер Kafka, который хранит данные и обслуживает клиентов. Topic — именованный поток событий. Partition — часть топика, представляющая упорядоченный журнал записей. Разделы позволяют параллелизм и масштабирование.

### 24. Что такое Consumer Group (группа потребителей) и как она влияет на масштабирование и распараллеливание чтения?
Consumer Group — несколько потребителей с одним `group.id`. Разделы топика распределяются между участниками группы, обычно один раздел обслуживается одним потребителем в этой группе. Это позволяет параллельно читать разные разделы. Разные группы могут независимо читать один и тот же топик.

### 25. Что такое реплика (Replica)? Чем роль Leader отличается от роли Follower?
Replica — копия данных раздела Kafka на брокере. Leader обслуживает основные операции с разделом, а follower реплицирует его данные и может стать новым лидером после отказа текущего лидера.

### 26. Что такое ZooKeeper (или подсистема KRaft в новых версиях) и какова его роль в архитектуре Kafka?
ZooKeeper ранее применялся для координации и хранения метаданных кластера Kafka. В новых версиях используется **KRaft**: встроенный кворум контроллеров на основе Raft управляет метаданными и выбором активного контроллера. В Kafka 4.x режим ZooKeeper больше не поддерживается.

### 27. Что такое Kafka Streams и как он отличается от написания Consumer-приложений?
Kafka Streams — библиотека для потоковой обработки: фильтрации, агрегации, объединения потоков и работы с состоянием. Обычное Consumer-приложение самостоятельно читает записи и реализует обработку, а Kafka Streams предоставляет готовые механизмы топологии обработки, окон и восстановления состояния.

### 28. В чем заключаются фундаментальные архитектурные отличия между RabbitMQ и Apache Kafka (модель хранения, маршрутизация, состояние сообщений)?
RabbitMQ обычно маршрутизирует сообщения через exchange в очереди; потребители подтверждают обработку, после чего сообщение удаляется из очереди. Kafka добавляет события в разделы журнала, хранит их согласно retention и отслеживает позиции чтения каждого потребителя по offsets. Kafka ориентирована на повторное чтение и поток событий, RabbitMQ — на гибкую маршрутизацию и доставку заданий.

### 29. Приведи примеры, в каких сценариях предпочтительнее использовать RabbitMQ, а в каких — Apache Kafka.
RabbitMQ удобен для фоновых заданий, рабочих очередей, маршрутизации уведомлений и RPC между сервисами. Kafka предпочтительна для журналов событий, телеметрии, потоковой аналитики, репликации событий и задач, где важно повторно прочитать историю.

### 30. Можно ли использовать RabbitMQ и Apache Kafka в одной архитектуре? Если — да, то за какие зоны ответственности каждый из них будет отвечать?
Да. Например, RabbitMQ можно применять для распределения команд и фоновых заданий между микросервисами, а Kafka — для длительного хранения событий и передачи потоков в аналитическую систему. При этом нужны согласованные правила доставки и обработки возможных дубликатов.
